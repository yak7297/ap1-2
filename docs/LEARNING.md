# 코드 이해하기

## 읽는 순서

`main.py → game.py → quiz.py → inputs.py → storage.py` 순서로 읽습니다. 처음에는 메뉴에서 퀴즈 풀기로 이동하는 흐름 하나를 따라가 보세요.

## 기초 문법과 실제 사용 위치

- 변수: 값을 이름으로 보관합니다. `correct`는 이번 게임에서 맞힌 문제 수입니다.
- `int`: 정답 번호와 점수 같은 정수입니다.
- `str`: 문제나 선택지 같은 글자입니다.
- `bool`: `played`처럼 참/거짓을 나타냅니다.
- `list`: `quizzes`처럼 여러 값을 순서대로 담습니다.
- `dict`: JSON으로 저장할 때 `"best_score": 80`처럼 이름과 값을 연결합니다.
- `if/elif/else`: 메뉴 번호에 따라 다른 메서드를 호출합니다.
- `while`: 올바른 입력을 받거나 사용자가 종료할 때까지 반복합니다.
- `for`: 문제나 선택지처럼 개수가 정해진 목록을 순회합니다.
- 매개변수: `read_number(prompt, minimum, maximum)`에 입력 문구와 허용 범위를 전달합니다.
- 반환값: `read_number()`가 검증한 정수를 `return`으로 돌려줍니다.

## 클래스와 객체

`Quiz`는 문제 한 개를 만드는 설계도입니다. `Quiz(...)`를 호출하면 실제 문제 객체가 만들어집니다. `__init__`는 객체를 만들 때 속성을 준비합니다. `self`는 현재 객체 자신입니다. `self.question`은 그 객체의 문제이며, `is_correct()`는 정답인지 판단하는 메서드입니다.

`QuizGame`은 문제 목록, 최고 점수와 메뉴를 관리합니다. 파일 처리는 `StateStore`에 분리했습니다. 최소 2개 요구보다 하나 많은 3개 클래스를 사용하지만 역할은 각각 문제/게임/저장으로 단순합니다.

## 저장과 예외 처리

`with path.open(encoding="utf-8")`로 파일을 열고 작업이 끝나면 자동으로 닫습니다. JSON은 리스트와 딕셔너리를 텍스트로 보관하는 형식입니다. `json.load()`로 읽고 `json.dump()`로 씁니다. 문제 객체는 직접 JSON에 쓸 수 없어 `to_dict()`로 바꿉니다.

`try/except`는 예상 가능한 실패를 안내하는 데 사용합니다. 예를 들어 `int("abc")`는 `ValueError`이므로 숫자를 다시 입력하게 합니다. `finally`는 정상 종료나 입력 중단 모두에서 저장을 시도합니다. 손상 파일을 읽으면 원본 백업을 시도한 뒤 기본 퀴즈로 실행합니다.

## 보너스: 랜덤 출제

`questions = self.quizzes.copy()`로 출제용 목록을 복사한 뒤 `random.shuffle(questions)`를 호출합니다. 원본 목록 순서는 보존됩니다. `shuffle()`은 전달받은 목록 자체를 바꾸고 `None`을 반환하므로 `questions = random.shuffle(...)`로 쓰면 안 됩니다.

## 커밋 메시지 규칙과 권장 커밋 단위 (평가 #12)

커밋 메시지는 `프리픽스: 변경 내용을 설명하는 한 줄 요약` 형식을 사용합니다. 이 프로젝트는 `Feat`, `Fix`, `Docs`, `Refactor`, `Test`, `Chore`, `Data`, `Merge`를 사용합니다. 별도 scope 표기는 필수가 아닙니다. 요약에는 변경한 대상과 동작을 적으며 `수정`, `작업 완료`처럼 내용이 드러나지 않는 표현은 피합니다.

| 프리픽스 | 사용 목적 | 이 프로젝트에 맞는 예 |
| --- | --- | --- |
| Feat | 새로운 기능 | Feat: 사용자 문제와 선택지 및 정답 등록 구현 |
| Fix | 잘못된 동작 수정 | Fix: Ctrl+C와 입력 종료 시 안내 후 안전 저장 처리 |
| Docs | README, 학습 설명, 캡처 | Docs: 원격 clone push pull 실습 캡처와 완료 기록 추가 |
| Refactor | 외부 동작을 유지하며 내부 구조 개선 | Refactor: 게임 진행과 파일 저장 책임 분리 (향후 적용 예) |
| Test | 동작을 확인하는 테스트 | Test: 저장 복구와 입력 예외 등 14개 검증 및 실행 증거 추가 |
| Chore | 프로젝트 기본 설정 | Chore: Python 퀴즈 프로젝트와 Git 기본 파일 생성 |
| Data | 제출용 퀴즈·점수 데이터 변경 | Data: 직접 추가한 퀴즈와 최고 점수 저장 |
| Merge | 기능 브랜치 통합 | Merge: 퀴즈 풀기 기능을 main에 병합 |

커밋 하나는 검토하고 설명할 수 있는 변경 한 단위로 묶습니다. 예를 들어 메뉴 입력 검증, Quiz 모델, 기본 문제, 플레이, 추가, 목록, 점수, 파일 저장, README 보완을 각각 나눕니다. 한 기능에 꼭 필요한 코드와 그 테스트는 함께 묶어도 됩니다. 관계없는 기능을 섞거나 개수를 채우기 위한 빈 커밋은 만들지 않습니다. 커밋 전에 `git diff --staged`로 포함 파일을 확인하고 코드 변경이면 관련 실행 또는 테스트를 확인합니다.

실제 분리 사례는 `a85ff88`의 플레이 구현, `39b8ee5`의 문제 등록, `47c5997`의 점수 갱신, `b5307a7`의 파일 입출력입니다. 기능별 커밋과 별도로 실제 브랜치 병합 커밋도 남겼습니다.

브랜치 전략은 안정된 결과를 모으는 `main`과 기능을 구현하는 `feature/이름`으로 구분합니다. `feature/quiz-play`에서 플레이 기능을 구현하고 확인한 뒤 main에 `--no-ff`로 병합했습니다. 이 기능 브랜치에는 출제·정답 판정·결과 표시가 들어 있고, 이후 등록·점수·저장·문서 작업은 main에서 진행했습니다. GitHub의 main 보호 규칙은 이 과제에서 별도로 설정하거나 검증하지 않았습니다.

<a id="class-design"></a>
## Quiz와 QuizGame를 클래스로 만든 이유 (평가 #13)

함수와 딕셔너리만으로도 이 게임을 구현할 수 있습니다. 이 프로젝트에서는 여러 문제의 데이터와 그 데이터를 다루는 동작을 함께 관리하려고 클래스를 사용했습니다.

- `Quiz`: 문제·선택지·정답을 한 객체로 묶습니다. 생성할 때 선택지가 4개이고 정답이 1~4인지 검증하고, 출력과 정답 판정을 같은 객체가 담당합니다. 문제를 딕셔너리로만 다루면 여러 함수가 `question`, `choices`, `answer` 키를 반복해서 알아야 하므로 오타와 검증 누락이 생기기 쉽습니다.
- `QuizGame`: 퀴즈 목록, 최고 점수, 플레이 여부라는 게임 상태와 메뉴·등록·플레이라는 동작을 묶습니다. 전역 변수를 여러 함수가 수정하는 대신 게임 객체 하나가 상태를 관리하므로, 다른 테스트에서 새 게임 객체를 만들어 독립적으로 확인하기 쉽습니다.
- `StateStore`: 저장 경로와 파일 입출력 책임을 분리합니다. `QuizGame(store=...)`로 임시 경로를 쓰는 저장 객체를 전달할 수 있어 실제 사용자 데이터를 건드리지 않고 저장·복구를 검증합니다.

| 비교 | 함수 중심 구현 | 현재 클래스 중심 구현 |
| --- | --- | --- |
| 상태 전달 | 함수마다 목록과 점수를 인자로 전달하거나 전역 변수를 사용 | QuizGame 객체의 속성으로 보관 |
| 문제 검증 | 딕셔너리 생성·변경 위치마다 검증 호출을 관리 | Quiz 생성 시 검증을 모음. 속성을 직접 수정하면 검증을 우회할 수 있으므로 생성/등록 경로를 사용 |
| 장점 | 아주 작은 프로그램에서는 코드와 호출 관계가 단순함 | 데이터와 관련 동작을 묶고 게임/저장 책임을 분리하기 쉬움 |
| 단점 | 기능이 늘면 인자가 많아지고 상태 전달을 추적하기 어려움 | 파일·클래스·self를 이해해야 하고 작은 문제에는 구조가 과해질 수 있음 |

이 과제에는 여러 문제와 유지해야 할 게임 상태가 있으므로 클래스 분리가 유용합니다. 상속이나 복잡한 설계 패턴은 필요하지 않아 사용하지 않았습니다.

## 클래스 상호작용과 책임 경계

1. `main.main()`이 `QuizGame()`을 생성합니다.
2. `QuizGame.__init__()` → `StateStore.load()` → JSON에서 `Quiz.from_dict()`로 문제 객체를 만듭니다. 파일이 없거나 손상되면 기본 Quiz 객체를 사용합니다.
3. `QuizGame.run()`이 입력 함수로 메뉴 번호를 검증하고 해당 메서드를 호출합니다.
4. `play()` → `Quiz.display()` → `read_number()` → `Quiz.is_correct()` 순으로 풀이하고, 완료한 게임의 점수를 계산합니다.
5. `QuizGame.save()` → `StateStore.save()` → 각 `Quiz.to_dict()` → UTF-8 JSON 임시 파일 작성과 교체 순서로 저장합니다.
6. `main.main()`의 `finally`에서도 저장합니다. 입력 중단으로 완료되지 않은 문제 등록·게임 점수는 반영하지 않습니다.

`inputs.py`는 빈 입력, 공백, 숫자 변환과 범위 검사만 담당합니다. 점수 계산이나 파일 저장은 하지 않습니다. `storage.py`는 파일 경로, JSON 형식과 상태의 일관성을 검증하고 읽기/쓰기·복구를 담당하며 사용자 입력은 받지 않습니다. `QuizGame`은 이 두 기능을 호출해 게임 규칙을 적용합니다.

<a id="json-tradeoffs"></a>
## JSON 선택 이유와 저장 방식의 한계 (평가 #18)

JSON은 문자열, 숫자, 참/거짓, 배열과 객체로 퀴즈와 점수를 표현할 수 있고 사람이 텍스트 편집기로 확인할 수 있습니다. Python 표준 라이브러리 `json`만으로 처리하므로 별도 패키지나 DB 서버가 필요 없습니다. 소수의 퀴즈를 한 사용자가 실행하는 과제에 적합합니다.

현재 구현은 시작할 때 파일 전체를 읽어 목록과 객체를 메모리에 만들고, 저장할 때도 전체 상태를 다시 JSON으로 변환해 씁니다. 따라서 문제 수가 커질수록 읽기/쓰기 시간, 파일 크기와 메모리 사용량이 증가합니다. 작은 항목 하나만 바꿔도 전체 파일을 다시 쓰므로 게임 기록을 계속 쌓거나 빈번하게 저장하면 비효율적입니다. 현재 저장되는 상태 크기에 비례하는 작업이며, 성능 수치를 측정한 것은 아닙니다.

또한 JSON 파일 자체에는 인덱스, 여러 레코드에 대한 트랜잭션, 동시 작성자 조정 기능이 없습니다. 현재 프로그램을 두 개 동시에 실행하면 각각 읽어 둔 상태를 저장하면서 나중 저장이 다른 쪽 변경을 덮어쓸 수 있습니다. 임시 파일 작성 후 `replace()`하는 방식은 기존 파일이 부분적으로 잘리는 위험을 줄이지만 동시 편집 충돌, 전원 장애에서의 완전한 내구성, 백업 정책까지 해결하지는 않습니다. 현재 버전은 한 번에 한 프로세스가 사용하도록 합니다.

| 상황 | 고려할 대안 | 이유와 주의점 |
| --- | --- | --- |
| 문제 수 증가, 검색·부분 수정 필요 | 표준 라이브러리 sqlite3의 SQLite | 필요한 행만 조회·수정하고 트랜잭션 사용 가능. 스키마와 마이그레이션 설계가 추가로 필요 |
| 게임 이력을 매우 자주 추가 | JSON Lines 등의 append 로그 | 매번 전체 이력을 재작성하지 않을 수 있음. 재실행 복원, 손상된 마지막 행, 로그 압축·정리 규칙 필요 |
| 여러 사용자·프로세스가 동시에 작성 | DB와 적절한 트랜잭션/동시성 제어 | 상태 덮어쓰기를 제어해야 함. 단순히 파일 확장자만 바꾸는 것으로 해결되지 않음 |

현재 과제에는 표준 라이브러리 JSON 저장을 유지합니다. 위 대안은 확장 시의 설계 선택이며 현재 구현했다고 주장하지 않습니다.

## 데이터 필드 변경과 호환성

현재 `StateStore.load()`는 quizzes, best_score, played, best_correct, best_total을 필수로 읽고 자료형과 점수 일관성을 확인합니다. 알려지지 않은 추가 필드는 읽을 때 무시되며 다음 저장 시 유지되지 않습니다. 필수 필드가 없거나 형식이 다르면 손상 데이터로 처리하므로 필드를 바로 삭제·변경하면 기존 파일을 읽지 못할 수 있습니다.

향후 필드를 바꾸려면 원본 백업, schema_version 도입, 이전 형식에서 새 형식으로의 변환, 기본값 처리, 이전 state.json 로딩 테스트를 함께 준비해야 합니다. schema_version과 자동 마이그레이션은 현재 구현에 없습니다.

## 요구사항이 바뀔 때 수정할 위치

| 변경할 요구사항 | 관련 파일과 함수/메서드 | 함께 확인할 사항 |
| --- | --- | --- |
| 메뉴 항목 추가 | game.py: QuizGame.show_menu(), run() | 번호 범위와 호출 연결 |
